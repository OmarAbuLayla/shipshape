---
concept: Comments that earn their place
summary: Good comments explain why; comments that repeat what the next line says only add noise and go out of date.
---

## The idea

Code already says *what* it does: `for path in files:` needs no `# loop over the files` above it. A comment earns its place when it says something the code cannot: why this approach, why this odd constant, what assumption this relies on, what would break if you changed it. Comments that narrate the code double the reading, and when the code changes the comment often does not, so it starts to lie.

A useful test: if a comment could be generated by reading the line below it, delete it, or replace it with the reason behind the line.

## Before and after

```python
# Before
# loop over the windows
for start in range(0, len(signal) - size, step):
    # append the window
    windows.append(signal[start : start + size])
```

```python
# After
# 50% overlap: each muscle onset appears in two windows, which helps the classifier
for start in range(0, len(signal) - size, step):
    windows.append(signal[start : start + size])
```

## Why engineers care

Reviewers read comments to understand intent. Narrating comments waste their time and suggest the code was not read critically; a single comment explaining a non-obvious decision is worth more than twenty restating ones.

## How Shipshape spots it

It compares each comment with the line that follows it and reports the project once it finds five or more comments whose words mostly repeat that line's names and keywords ("loop over files" above `for f in files`). It is a heuristic: it can miss restating comments that use different words, and it does not judge whether a "why" comment is correct.
